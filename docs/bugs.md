# Defects and inherited behaviour

What is known to be wrong, or deliberately different, in the library: the defects of the original implementation that the port reproduces, the places
where it deviates on purpose, and the candidate defects found while reading the code.  Source comments point here as `docs/bugs.md` + a section letter or
a V id (the `@bug` / `@warning` markers in `src/` are the in-code side of this register).  The section letters are kept from the original register and are
therefore not contiguous.

* **C** - known, deliberately kept differences and open items.
* **G .. S** - defects and hazards of the original in the voice, fax and dp-registration code, which the port reproduces (deviations marked).
* **V** - candidate defects, one row per defect (V01 ..), with evidence, reachability, consequence and the 64-bit behaviour; V.0 is the short list worth
  reporting upstream.

Evidence labels used in V: `R` = reproduced by a run, `C` = found by reading the code only.  Defects that were found and fixed are not listed here.

## C. Known, deliberately kept differences and open items

* `FSE_decision_16pt` (4800 bps) magnitude: the original indexes `DECv32_MAG9600 - 2 + 2*((|I|+|Q|)>>1)` -> 4096/8192/12288 shorts past the table (layout-dependent memory); the port writes 0.  Live 4800 passes (20/20).  Cannot be reproduced.
* `FSEv32_decision` (6 shorts, 3 relocations in the original): the port's copy is zeros.  A scan of every relocation of the original object finds no reference to the symbol: dead data.
* `src/v8/v8.c` `v8handshak` tx-phase `default:` / rx-phase `default:` call `abort()` where the original does nothing.  Audit: the only values ever stored in obj+0x9d4 are 5, 6, 0x17, 0x2b, 0x2d (grep of every store); unreachable unless the object is corrupted.
* `v32_process`, `v32_unported()`: the V.32 outer glue is an `abort()` stub; the hybrid keeps the original's glue (renamed `dp_v32_init/exit`).
* Debug text (`dsplibs_debug_level > 1`, `slmodemd -d2`) of ported functions that the port still omits - found by comparing, per ported function, the format strings referenced by the original and by the port objects; all are `-d2` log lines, none changes DSP output:
  `B103AnswerNextState` / `B103OriginateNextState` (state-name prints `B103_STATE_*`), `DemodDataV32` ("v32 low sig energy"), `V32AnsNextState` / `V32OrgNextState` / `V32RngInitNextState` / `V32RngRespNextState` ("state %s(%d)"),
  `V32FP_control` ("Patch: set ctl_ptr->vxx_ctl.options.retrain"), `V32FP_recreate` (the "V32FP Config" line), `V8SetMessage` (two lines), `v32_create` (config / delay lines), `v32_data` (V32_MSG_NO_CARRIER lines), `v32_process` (stub), `VPcmV34Progress` ("Estimated DC").
  Not fixed (each needs the exact argument list of a tail call plus a `-d2` scenario).  The C++ rows (P/V/Z) showed no absent string by this method.
  (Method: for every function of the original that also exists as a port symbol, the string literals it references that occur in no port object's .rodata.)
* `V22_SRE_recover` (original) has NO `count > 0` guard in its partial-call path (`count < rem`): a negative `count` calls `sysdep_memcpy` with a huge length (the FSE sibling `V22_FSE_receive` has the guard).  The port reproduces the original (it would crash the same way); callers pass block sizes >= 0 (not tested: the real original crashes).  Also `V22_FSE_receive` / `V22_SRE_recover` write one output per symbol into 0x1c-byte (FSE) / caller buffers without a bound: the FSE's I / Q buffers hold 14 symbols (count <= 84 per call); the harness refuses larger counts.
* Remaining `unk*_` regions, the 67 aliasing-sensitive objects (see `flags.mk`) and the detector-block 64-bit tripwire (`detectorinit` stores the coefficient pointer in a 4-byte slot, `tone_detect` reads it through `PTR(det,0)`) are layout / 64-bit work, not defects of the 32-bit port; V04 tripwire not changed (needs a struct conversion).

## G. voice DTMF / beep: original defects, all on paths the callers do not reach (port deviations marked)

* `beepgen_start_dtmf('!')` calls `beep->cb124(ctx, 0x18)` without a NULL check (the duration of a '!' digit): the original segfaults when the callback record's fourth word is NULL.  Port: keeps the duration instead (guarded child in a test: the original dies, the port returns).
* The BeepGen queue holds 20 entries (`BeepGen.q[20]`, +0x2c .. +0x11b) and `beepgen_start_beep / _start_dtmf` never check `count`: the 21st entry overwrites the three callbacks and the divisor (+0x11c .. +0x128), later ones the heap behind the 0x12c-byte object.  Port: an entry that does not fit is ignored (`beep_queue`; port-only check in scenario 3, not compared with the original).
* `beepgen_create` leaves `n`, `limit`, `div` and the queue uninitialised (they are written by the first `start_*`); `create_dtmf` leaves bytes 0x80 .. 0x8f and 0x96 .. 0x97 of the DTMF object alone.  Not a defect for the callers; the harness memsets stack objects before it hashes them.
* `beepgen_start_*`: `dur * 8000` is a 32-bit multiply (wraps for dur > 268,435) before the signed division by 10 / 100; reproduced.
* `dtmf_test` returns `esi + 4 * ebx - 16` and `ebx` starts at 0: when every energy of the high group is >= 1.0e38 (the "no minimum yet" start value) a result in -16 .. -1 is possible; `dtmf_detect` would store it as a digit code.  Reproduced (harness: energies at / above 0x7e967699).

## H. voice API: VOICE_* glue + voice engine: original defects and hazards (the port reproduces them; deviations marked)

* **VOICE_process crashes at 8000 Hz.**  `VOICE_create` accepts 8000 Hz and leaves both RcFixed pointers NULL; `VOICE_process` calls `RcFixed_Resample(rcIn, ...)` / `RcFixed_Resample(rcOut, ...)` unconditionally (SIGSEGV on the first block).  Port: identical (the call is not guarded; r17_e2e scenario 4 runs it in a forked child and requires a crash in both).  slmodemd's voice path only works at 9600 Hz (`m->srate`).  Suggested fix for the switch-over: skip the converter calls when the pointer is NULL (an identity copy).
* **48000 Hz overflows the rings.**  `blk = srate / 50 = 960` against two 384-sample rings: `VOICE_process` writes behind the glue block.  `VOICE_create(48000)` itself is tested; VOICE_process at 48000 is not (undefined in the original).
* **VOICE_process advances `in` / `out` by n BYTES per block** in its outer loop (the inner copies advance by 2n): a call with more than one block (count > srate / 50) reads / writes shifted data from the second block on.  Reproduced (r17_glue scenario 2: counts up to 577); slmodemd calls with one block.
* **voice_tx reads 0xde bytes into the 0xc8-byte transmit buffer** when the rate word is not 8000 (7200 Hz: 0x90) and the fifo read overlaps the first floats of the staging buffer at +0x100.  Reproduced by the union layout (rate is always 0x1f40 in production).  `voice_tx` with `*a6 > 400` and vls 1 / 2 reads / writes past the 400-float staging buffer (the harness stays inside).
* **voice_rx ignores `silence_is_more_then`'s result**, takes `a1` as 16-bit PCM from the tty in the vls 1 / 3 modes (reads garbage beyond the bytes the tty delivered), and its `byte == 0x10` doubling branch is unreachable: linear2ulaw of a 14-bit value never returns 0x10 (r17_voice scenario 0 asserts it for -8192 .. 8191).
* **voice_create failure paths**: FDSP_DP_Create / FIFO8_create / TONE_create / cadence allocation failures crash the original (30 of the 60 allocation indices of VOICE_create); the cleanup `if (v->sil) silence_delete(v->sil)` is dead; `sysdep_free(NULL)` is called at two indices (harmless with the real sysdep_free).  Port: returns NULL cleanly except where RcFixed_Create crashes (indices 1 - 4) and at the same `sysdep_free(NULL)` index 14.
* **STRM_VCE_GetFDSPEnvironmentalParams prints the OLD values of its output words** ("voice: StrmVCE old: *psFarEchoDelay %d ,*psNearEchoDelay %d"), which are the UNINITIALISED stack variables of voice_create / voice_command (debug level > 1 only): the numbers differ between builds; the harness masks them.
* The original re-reads or caches memory words at fixed points (the count words `*a6`, the mode / abort / etx fields, the debug level); the port follows with `BARRIER()` (compiler barrier) where the original re-reads; the unit harnesses rewrite those words from inside debug messages / the beep recorder to pin this (a `cx = *a6` deletion is killed; the re-read feeding the dead `*a5 = cx` store before `*a5 = 0` is not observable).
* The glue passes `uninitialised` stack arguments only for `voice_command(9, ...)` (ABORT: the engine ignores the array).

## J. V.29 transmit: original defects and hazards (the port reproduces them)
- V29TX_create mallocs the circular `buf` block on every create: a re-create of a live engine (control 0xd bit 1, create(o, o)) leaks the previous one.
- Re-creating a live engine with MORE FIFO frames (cfg word 5: 1 -> 2) overruns the FIFO buffer (FIFO_create keeps the old buffer, takes the new size); probed in a forked child .

- v29tx_message(m, 8) reads one pointer past V29TX_MESG (V29TX_CTL[0]); the 7200 bit/s message says "7600 bps".

## K. V.29 receive: original defects and hazards (the port reproduces them)
- V29RX_create leaves `hdx.s1c` (+0x1c) uninitialised in a new hdx block (heap garbage); DataCarrierDetectV29 tests it (0 = the normal path A, anything else = path B with the V.21 carrier timeout).  The port zeroes it; the harness defines it right after every create on both sides.
- The SRE output buffer is 164 samples (0x148 bytes): a receive block of >= 183 samples makes the SRE emit more (heap overrun, "wrote outside a block" in the red-zone probes n = 183 .. 200 of scenario 4); the "ERROR: SRE buffer violation" text is printed only above 164.  The harness keeps normal blocks <= 120 / 150.
- V29RX_create dereferences NULL when malloc fails: signal 11 for the failing allocation #0 (object), #1 (hdx), #4 .. #23 (the MTD / tone / AGC / bundle / MRF / SRE / FSE sub-objects); #2 / #3 (the two 0x140 byte hdx buffers) do not crash at create (they are used later: tone killer copy, carrier detector copy).
- `v29rx_create` returns the bits-per-symbol code 3 (7200) / 4 in eax, NOT the engine handle (unlike v27rx_create); the engine only goes into the VMI object.  `v29rx_message(m, 8)` reads one entry past V29RX_MESG (V29RX_CTL[0] = 0x25800000): the port stores NULL.
- A rate word other than 7200 / 9600 sets rate index 1 and the error flags (st byte 3, flag 2), which a few stores later are overwritten by the common `st = 0x5002`: the error is never visible (the two rate branches of V29RX_create only differ in these dead stores).
- V29RX_status rebuilds the record's flag byte completely (bits 1, 3, 5 from bundle words w18 / w0 / w20, 0x50 set) but leaves the second flag byte `b15 &= 0xfe` as a read-modify-write of the caller's garbage.
- GetSNRV29 = 14 - fse.e52 is a real estimate: RxHdxDataV29 / RxHdxPrtcolV29 set the "SNR low" flag (b[1] bit 7) when it is <= 8 (V.27ter's GetSNRV27 is the constant 10).

## M. V.17 transmit: original defects and hazards (the port reproduces them)
- V17TX_create never initialises the encoder select (bundle +0x8c), smc.w4 / w0a / k and the bundle's two leading words (heap garbage); ModDataV17 indexes its encoder table with the select, so a modulated block before SetEncoderV17 / SetTxModeV17 would jump through garbage (the state machine always selects an encoder first).
- A control re-create (byte 0xd bit 1) after SetTxModeV17 resets the pulse shaper to the 5 entry SMCv17_IMAP4 / QMAP4 maps and the no-carrier code to 4 but keeps the trellis encoder (codes up to 127): the pulse shaper then reads past the map until the next SetTxModeV17 (the real machine only re-creates before SCR1; the harness repairs it).
- V17TX_create dereferences NULL when malloc fails (fresh create: allocations #0 .. #9; #4 is the SGD object inside SGD_create, which the port guards); re-creating a live engine with MORE FIFO frames (cfg word 5) overruns the FIFO buffer; a supplied object without a bundle makes the PPS init read / free garbage (host-layout dependent).
- SetTxModeV17 indexes V17TX_SYM_SIZE (and TxNextStateV17 V17TX_PATTERN_SCR1) with hdx.rate without a range check; the port reads 0 for an out-of-range rate in SetTxModeV17.
- v17tx_message(m, 10) reads one pointer past V17TX_MESG (V17TX_CTL[0] = 0x3840); the port stores NULL.  The message "V.17 Protocal Transmit Mode" is misspelled in the original (kept).
- v17tx_create returns the rate word (cfg s[1]), not the engine handle.

## O. FAXVMI: original defects and hazards (the port reproduces them)
- FAXVMI_create dereferences NULL when malloc fails (NULL object: allocations #0 object, #1 framing state, #2 modem object, #3 ring, #5 bit buffer, #6 scratch buffer all SIGSEGV; #4 the HDLC receive frame buffer only when the config has s0c > 0; with s0c == 0 the NULL buffer is never touched).  The port has no guard (same outcome, probes `PROBE create malloc #k` of scenario 4).  A caller-supplied object keeps its ring / frame buffer and their sizes (the create only zeroes them): a supplied object with garbage pointers or sizes crashes.
- The ops tables and the framing tables are indexed by the 16 bit mode (0 .. 2) / modem id (0 .. 12) without a range check: the original reads the neighbouring .rodata table (mode 3 on the unpack table calls faxvmi_simp_pack ...).  The port indexes its own arrays (undefined past the end): callers must stay in range (the harness does).
- faxvmi_hdlc_unframe, repair by shifting: the shift loop reads frm[flen_old] (one 16 bit word PAST the collected data; past the buffer when the frame filled it: flen == frm_size, the buffer is 2 * s0c bytes); the overflow test is `total + flen >= s0a` with a `total` word that is never changed from 0 (so the per-call total of the output records is not bounded: only each frame by s0a); an output overflow leaves `flen` unchanged (the next frame is appended to the stale bytes); a run of seven or more ones is NOT an abort (the bits are collected like data); a frame that cannot be repaired is delivered as an empty record ([0]).
- faxvmi_hdlc_frame with debug level > 1 reads ring[size] (one word past the ring) when the frame length word is in the last slot (rd == size - 1) and the three bytes of the frame name from rd + 1 without a wrap check on the first index.
- faxvmi_write_fifo / write_frame take 16 bit counts and lengths: a negative count (write_fifo) runs until the ring is full; a frame length >= 0x8000 (negative short) makes the CRC loop and the data copy run ~65,535 words (the copy stops when the ring is full: the overflow branch), reading far beyond the caller's buffer.  The frame data words are copied whole (16 bits) and the CRC is computed over the words << 8 (words above 0xff change it).
- faxvmi_asyc_pack / simp_pack / hdlc_frame write m->s0c words of m->s0e bits into the 50 short bit buffer (0x64 bytes) without a bound; the modems set s0c <= 0x30 and the null modem 0x32.  null_process copies *cnt shorts into the 200 short scratch buffer m->buf0 without a bound.
- FAXVMI_control's reset path stores w34 / w38 and the final stores overwrite them (dead stores); FAXVMI_create copies the DWORD at framing +0x1c (transmit bit count word + two garbage bytes) over +0x2c.  FAXVMI_delete frees buf0, bits, frame buffer, ring, modem object, framing state and the object itself, also for a caller-supplied object.
- Observed through the ENG scenario 1 (both sides): a V.29 transmitter control re-create (control byte 0xd bit 1) leaks one block (reported as `LEAK elife 1 live blocks`); not a defect of this function.
- The V.17 receiver's hdx.s20 flag is heap garbage in the original (BUGS N): the ENG harness defines it right after every create on both sides.

## Q. T.30 / HDLC receive: original defects and hazards (the port reproduces them unless noted)
- _init_receiver with a modem value other than the twelve known ones leaves the class and the rate uninitialised (stack garbage) and then indexes init_vmi_data_rx_modem with it: undefined.  The port uses class 0 / rate 0.  Not tested.
- _init_receiver dereferences NULL in four situations (forked probes: original SIGSEGV, port returns without touching more): the sysdep_malloc of the 0x18 byte data config block fails (probe kind 0; the init function writes through it), FAXVMI_create returns NULL (kinds 2, 8, 9: `[eax+0x28]`), and an object with a config block but no data channel (data_cfg != NULL, data_vmi == NULL: the restart path reads data_vmi->m; kinds 6, 7, also with a class change, which skips the deletion for a NULL channel).  _delete_data_rx_modem dereferences o->data_cfg without a check.
- The modem-id based record selection of the restart path (0xc V.17, 0xa V.29, otherwise V.27ter) and the class based engine pokes that follow (AGC words are poked only into a NEWLY created engine, the carrier flag always) are separate decisions: an object whose config block id and class disagree pokes the wrong engine layout (not reachable through the API).  The V.29 record is copied from 4 words of V29RX_CTL, the fifth word of the stack record is garbage (never read by V29RX_control).  The rate goes into the HIGH half of word 0 for all three receivers (the transmit side uses the low half for V.29 / V.17).
- _hdlc_emulate_receive_state keeps the frame lengths of the superframe in a 12 entry stack array: more than 12 records overrun it (an original stack smash; the port's array holds 256 entries, the harness stays below 12).  A superframe fill past the records makes it hand out the next buffer words as a frame (the length word is taken from whatever follows: up to 0xffff bytes are read past the object; the harness avoids it).  sf_fill (w12d0) is not range checked anywhere: _hdlc_receive_between_buffers_state tests only `fill + len + 1 > 0xff` (a negative or garbage fill indexes outside buf[]), and copies with a 16 bit index (a length above 0x7fff that passes the test with a negative fill never ends).
- The S7 timeout of _rx_look_carrier_state / _hdlc_receive_look_carrier_state is w12b4 * 8000 / *n_in with a SIGNED division (SIGFPE for *n_in == -1 when the product is 0x80000000; 0 for *n_in == 0 is handled: w12b4 * 50).  While the calling tone is on (cng_on != 0) the HDLC look carrier state never evaluates the timeout.
- _handle_data_input / _handle_hdlc_input store words at out[0 ..] / out[w1250 ..] without a bound (only the 20 zero words after DLE ETX are limited to index 0x7ff); a frame stream longer than the buffer overruns the object.  _handle_data_input counts every byte it sees in a write-only .bss word (the original-LOCAL `temp.0`, port fax_handle_data_input_count).  After DLE ETX the data input ignores everything until w12b0 is cleared; a DLE followed by anything but DLE / ETX drops that byte.
- _hdlc_receive_state with the frame length word 0 (bad CRC) reports w123c = 2 and goes to state 6 without a DTE report; with a carrier loss and a frame in the same call it reports the frame twice (the no-carrier branch passes an empty frame, then the frame branch overwrites *p7).

## R. fax class 1 layer + the FAX_* entry points: original defects and hazards (the port reproduces them unless noted)
- fax_class1_create(NULL, cfg) mallocs the 0x12f4 byte object WITHOUT clearing it and initialises only the words it needs (`chan` 0x1244, the data modem class `w1248`, the receive result words `w123c` / `w1240` partly, w1230 .. w12ac, the timers ...): they hold heap garbage.  The debug lines "Initializing TX modem, MODEM_IDX = %d" / "Initializing RX modem receiver, MODEM_IDX=%d" print the uninitialised class word of a fresh object (the ENG harness stores 0 there after every create: its heap pattern depends on the host).  A fresh object whose garbage `chan` happens to be 1 with `modem_sel` set to a class value and no data channel would make fax_class1_progress dereference NULL; unreachable through the API (FAX_class1_command forwards FTH / FRH only with parameter 3, and FTM / FRM set `chan`).

The port frees what it allocated and returns NULL (deviation, documented).  The results of the two FAXVMI_create calls are not checked either: a failing create leaves a NULL channel (fax_class1_delete skips it; the first FAXVMI_process of the transmit / receive states would dereference it).  The port keeps that.
- The answer tone length of the debug line "Answer tone length %d ms" is stored as cfg.w10 / 20 (frames of 20 ms; the code multiplies by 0x66666667 and shifts by 3), default 150 frames = 3 s; FAX_create never sets it.
- fax_class1_command: a command number below 0 that is <= 5 (signed) prints the CALLER'S EDI REGISTER as the command name in "At %2d.%02d[sec] %s %d" (undefined; the port prints an empty name; the harness keeps such commands at debug level <= 1); every command except RH (3) clears the superframe fill sf_fill (w12d0), unknown commands (> 5) included; the lookup of the command / state / status names scans the whole table (the LAST entry with the key wins).

## S. prop_dp_init / prop_dp_exit: hazards of the original (the port reproduces them)
- prop_dp_init discards the return value of all seven dp_*_init (modem_dp_register returns -1 when the slot is already taken or the id is unknown): a second prop_dp_init without prop_dp_exit "fails" silently and returns 0 anyway.  prop_dp_exit returns 0 too (the C callers declare it void; the port keeps the int 0).

- DP_FAX is never registered (FAX has no dp glue); prop_dp_init registers 7 pumps.
- No state, no allocation, no argument: nothing in the pair is word size dependent.  The link without the original needs the i386 only `regparm(1)` forwarder (`getMPrecvdBits, the original's LOCAL C++ function called by src/vpcm/vpcm_phase34_reneg.cpp); at -m64 the attribute is ignored and the same file links (experiment).

## V. Candidate defects, consolidated

Source: the notes written during the porting passes (comment, member-access, host-interface and layout passes) and the `@bug` / `@warning` markers in `src/` (see "Marker census" at the end).  Labels such as CM2 or RL6 in the evidence columns name those passes; their records are not part of this repository.
